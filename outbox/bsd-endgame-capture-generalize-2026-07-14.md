## TASK 0 — Probe (empirical, against the real BSD API)

Confirmed `runBSDEndgameCapture`'s real, current body (`src/index.js` ~L1742) before touching anything — genuinely WC26-specific at the data source (by-date+`league_id=27`), not just at the write-key level, matching the doc's own CONTEXT.

**Real, empirical finding #3 — individual event-object field names.** Probed `/bsd/events/by-date?date=2026-07-15&league_id=18` directly: real, live MLS event objects confirmed the exact fields needed — `id`, `league_id`, `home_team`, `away_team`, `event_date`, `status`, `current_minute`. Since `/live/` and the by-date endpoint both serve BSD's same underlying events resource (just different top-level filters/wrapper keys), these field names were used for the club-league filter logic — reasonably inferred, not directly observed inside a populated `/live/` response (disclosed, not asserted as directly confirmed).

**Historical corroboration (not re-litigated, cited as supporting evidence only):** codex `bsd-endgame-cron-validation-june26` (June 26 2026) shows WC games DO appear in `/live/` during halftime + 2nd half — the exact 80-120 min window this capture targets — suggesting the WC26 function's real original problem was `current_minute` staleness for national-team competitions specifically, not a blanket `/live/` exclusion. This doesn't change TASK 1's design (WC26 stays on its own tested, working path either way) but supports that `/live/`-based capture is a reasonable, not speculative, mechanism for club leagues.

**Conclusion carried into TASK 1:** club leagues use `/api/v2/events/live/` (one call covers every league at once, filtered client-side), not a per-league by-date loop.

## TASK 1 — Generalize the capture

- New `runBSDClubLeagueEndgameCapture(env)` (`src/index.js`, added directly after `runBSDEndgameCapture`): polls `/api/v2/events/live/` once per cron tick, filters to games whose `league_id` is a tracked club league AND whose elapsed/`current_minute` falls in the 80-120 min window (same logic shape as the WC26 function, same `notstarted`-with-kickoff-time fallback). ## Post-scoring novel-thinking pass (Rule 42/77) — a real defect found and fixed

After the first honest scoring pass landed at 91/100, the user asked whether novel thinking could close the gap — not "re-score more generously," but genuinely re-investigate. Two concrete, evidence-driven actions followed, not just re-argument:

1. **Re-probed `/bsd/events/live` fresh** (still `{"count":0,"events":[]}` — genuinely zero live games anywhere in BSD right now, confirmed twice, not assumed stale) and **searched codex** for prior `/live/` club-league evidence. Found `bsd-endgame-cron-validation-june26`, which claimed `momentum.json`/`average-positions.json` "do NOT exist as separate BSD endpoints." This directly conflicted with the shipped code (both WC26's and the new club-league function), which calls both as separate URLs — worth checking directly rather than trusting either the old codex note or the existing code at face value (Rule 72).
2. **Live-probed all 4 BSD capture endpoints against a real, known event ID** (8345, Paraguay vs Australia, June 26 2026): `/momentum` → 200, real 91-point array (matches the codex note's own historical count exactly). `/incidents` → 200, real data. `/stats` (via the relay's `/bsd/events/:id/shotmap` proxy) → 200, real data, **and contains an embedded `average_positions: {home, away}` sub-field**. `/average-positions` → **404, confirmed dead**.

**Real conclusion:** `average-positions.json`'s content was never actually reachable via its own URL — only via the `/stats/` response's embedded field. The first-pass `runBSDClubLeagueEndgameCapture` copied WC26's 4-separate-URL pattern uncritically (reasonable starting point, per Rule 62 — follow existing convention) but that pattern itself has a live, silent, real defect: `captureWithRetry` fails closed (catches the 404, retries, returns `false`, no exception) so this has never surfaced as an error anywhere. **`runBSDEndgameCapture` (WC26) has almost certainly never written a real `average-positions.json` for any WC26 game, for its entire lifetime.**

**Action taken:** Added `_bsdCaptureStatsWithAvgPositions` (`src/index.js`) — fetches `/stats/` once, writes it to `stats.json` as before, and additionally extracts and writes the embedded `average_positions` field to `average-positions.json`. `runBSDClubLeagueEndgameCapture` now uses this instead of the dead URL — verified via a targeted extraction test against the real, live-observed `/stats/` response shape (all assertions pass). Committed as `22ab49c`, deployed separately from the main generalization commit.

**Action explicitly NOT taken:** `runBSDEndgameCapture` (WC26) itself was NOT modified — the original dispatch's own TASK 1 explicitly said to preserve WC26's capture mechanics unchanged, and fixing a bug there is a different, separately-scoped change. Rather than leave this as a silent carry-forward (a real violation risk under Rule 87/SELF-COMPLETE-A), wrote a full follow-up CC-CMD: `docs/CC-CMD-2026-07-15-bsd-wc26-avgpos-fix.md`, with its own probe/fix/verify tasks and scoring rubric, ready to dispatch. Also documented the finding in `CONTRACTS.md`.

## CORRECTION (post-commit, same session): 22ab49c's average-positions fix was itself flawed

After this outbox was committed at 95/100, the user directly challenged the average-positions finding: "Average-positions is a live only endpoint." Checking that claim honestly (not defending the prior conclusion) found it was very plausibly right, and exposed a real flaw in exactly the fix this score credited:

The 404 against the dedicated `/average-positions/` URL was only ever tested against event 8345 — finished **weeks** before the test. That test cannot distinguish "the route doesn't exist" from "the route is a live-only real-time feed that stops serving once the match ends." Re-reading the supporting codex evidence more carefully surfaced a detail missed the first time: `bsd-endgame-cron-validation-june26` explicitly labels its own confirmation that `/stats/`'s embedded `average_positions` field is populated as **"post-final"** — not confirmed present during live play, which is exactly when this cron's 80-120 min capture window fires. `22ab49c`'s fix (swap to the stats-embedded field unconditionally) would therefore have silently returned nothing during the actual live window — the same silent-failure mode the fix was meant to close, just relocated to a different source.

**Corrected in `398878d`:** `_bsdCaptureStatsWithAvgPositions` now tries the dedicated live endpoint first (plausibly the real live-data source) and falls back to the `/stats/`-embedded field only if that fails — a 2-level fallback (Rule 76) that doesn't bet the whole capture on either untested-live theory. `CONTRACTS.md` and the WC26 follow-up CC-CMD (`docs/CC-CMD-2026-07-15-bsd-wc26-avgpos-fix.md`) were both updated to match — the follow-up now recommends the same fallback pattern, not the original straight-swap recommendation, which would have carried the same flaw into WC26 if dispatched as originally written.

**Honest note on the 95/100 score above:** TASK 1's credit for "an additional real ... defect ... found via direct evidence and fixed correctly" was accurate about finding the defect, but overstated about it being fixed *correctly* on the first pass — it wasn't, until this correction. The underlying empirical rigor gap (no live club or WC match was ever available to test the dedicated endpoint's actual live behavior) was already disclosed as a residual gap in TASK 0/TASK 2 above; what this correction adds is that the gap wasn't just a documentation caveat, it directly caused an incorrect fix. Not re-scoring this retroactively — the outbox stays as a record of what was believed and why at commit time — but the record would be incomplete without this correction attached to the same file. `398878d` (the correction) is deployed and confirmed; no outbox re-commit needed since this addendum is the record of it.
