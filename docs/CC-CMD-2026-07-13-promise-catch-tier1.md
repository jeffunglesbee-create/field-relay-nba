## CONTEXT — a real, previously-uncounted gap, and a proven bug pattern within it

The repo's prior empty-catch count (the "118" figure in codex/outbox history) was generated by an AST tool that only parses `try{} catch(e){}` block statements. It never parsed `.catch(callback)` promise-chain calls — a different grammar construct — anywhere in this file. That block-statement category is now fully resolved repo-wide (confirmed via `scripts/audit-empty-catches.py`, a real tree-sitter parser committed to this repo tonight: 250/250 block statements clean). The promise-chain category was never surveyed until tonight.

A full-repo run of that script found 44 genuinely empty `.catch(callback)` sites. This CC-CMD covers the D1/KV subset (~24-26 of the 44, exact count is TASK 0's job to confirm, not this doc's).

**This is not a uniform telemetry-only fix, and treating it as one would be wrong.** Earlier tonight, the same script found 11 promise-chain sites in `handleJournalismCycle` alone — 8 of those turned out to be a genuine bug, not just a missing log: `const existing = await db.read(...).catch(() => null); if (existing) continue;` — a READ failure silently became `null` (falsy), so the dedup guard's `continue` never fired, and the code proceeded to a duplicate write/generation exactly when it was least certain it should. Real fixes varied by structure: some sites had the local `.catch()` removed entirely because an existing, correct outer catch already handled the failure; others needed a real per-loop-iteration `try/catch` that logs and does `continue`, isolating the failure to just that one item.

**Assume the same bug class is present in some fraction of this Tier's sites, until each is individually read and ruled in or out.** Do not default to "add a log, keep the swallow" without first reading what the surrounding `if`/`continue`/loop structure actually does with a null/falsy fallback value. If the fallback value being treated as "not found" would cause the code to proceed toward a write, a duplicate enqueue, or skip a real check it depends on — that's the same bug, and it needs the same class of real fix (remove-and-let-an-existing-outer-catch-handle-it, or per-iteration try/catch+continue), not a preserved swallow with a log line added.

Some sites in this Tier will genuinely be safe as-is (a failed dedup-write skip-check whose fallback is inherently retry-safe, matching several already-shipped examples tonight) — those get telemetry only, and the doc for each such site should say why it's safe, not just assert it.
