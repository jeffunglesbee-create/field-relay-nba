## Item 4 — Squiggle's User-Agent requirement (DECIDED 2026-11-26: the relay sends a contact address; built as a Worker secret the owner sets)

Squiggle's Requirements, item 1 (https://api.squiggle.com.au/, v1.14.0, read in full on 2026-11-26): "Set your bot's UserAgent to something that identifies it and contains a contact email, e.g. \"Dan's Tipping Comp - dan@example.com\"". Its changelog, 1.13.0 (Apr 2026): "Requests from bots that fail to comply with the UserAgent requirement may now be blocked at edge level (particularly if they run from a server farm) and won't receive a nice explanation why, since there are so many that even serving a nice error taxes system resources." Until 2026-11-26 `SQUIGGLE_HEADERS` (`src/index.js`, `src/wp-resolver.js`) sent `FIELD-Global-Sports-Intelligence/1.0 (jeffunglesbee-create/jubilant-bassoon)`: a name and a repository, no email. **Measured 2026-11-25 01:20Z (run 45524946667, `afl-finals-live-check.yml`): Squiggle answered HTTP 403 to a GitHub runner for every `?q=tips;year=2026;team=N;source=8` read, with that User-Agent**; the relay's Cloudflare egress is served (the deployed relay returned the finals' own tips, and its `/squiggle` pass-through answered 200 for a team season never read before and for a cache-busted query). Nothing before this read Squiggle from a runner (Task 0 and the reviews read it through Cloudflare; the round-discovery live check stubs Squiggle). The two runner-side readers, the live check and checks 12 and 13 of the staged verifier, go through the relay's `/squiggle` route (`afl-finals-live-check` run 45525556353: 6 of 6, 7 of 7). Whether a contact address would also let a runner read Squiggle directly, or would hedge the relay itself if Squiggle ever extends the block to Cloudflare's egress, is unmeasured (the relay then serves null and warns, never a wrong tip). The finals work adds volume (a finals day is two Squiggle reads and no Kali read where it was one of each), not a new identity.
**Decided 2026-11-26 (owner: "Yes, contact address", and the account address when asked which).** Built: every request the relay makes to Squiggle (`src/index.js`: the round read, the finals read and the `/squiggle` pass-through; `src/wp-resolver.js`: the resolver's two reads) takes its headers from `squiggleHeaders(env)` (`src/afl-squiggle.js`), whose User-Agent is `FIELD-Global-Sports-Intelligence/1.0 (jeffunglesbee-create/jubilant-bassoon) - <address>` (Squiggle's own example shape: a name, then " - ", then the address as the last token; without the secret it is exactly the User-Agent sent before). **The address is not in the source or the git history:** it is the Worker secret `SQUIGGLE_CONTACT`, because a guard on this session refuses to let the account address pass through a command next to a client identity, and because a secret is also the better place (no edit and no deploy to change it). The value is trimmed and must be one plain address (printable ASCII: a local part of RFC 5322 atext characters with dots only between them, one @, a dotted domain of letters, digits and hyphens, at most 254 characters: no spaces, quotes, brackets, commas, semicolons or backslashes); unset or malformed it is left out, said once per isolate in the logs, and the request is still made with today's User-Agent, so a missing secret degrades to the state before this and nothing breaks. Each `/squiggle` answer to a forwarded query carries `X-FIELD-Squiggle-Contact: set | unset | invalid` (a word, never the address; `CONTRACTS.md`), so the owner's step and a typo are visible.
**The owner's step, which nobody else can do (about a minute):** Cloudflare dashboard -> Workers & Pages -> `field-relay-nba` -> Settings -> Variables and Secrets -> Add, type **Secret** (not Text), name `SQUIGGLE_CONTACT`, value the address, then **Deploy** (Cloudflare's own last step: until it is deployed nothing changes), or `npx wrangler secret put SQUIGGLE_CONTACT --name field-relay-nba`, which deploys at once. A Secret survives every deploy and `deploy.yml` does not touch it (its wrangler step puts only the eleven secrets it lists); a plain-text variable of the same name would be deleted by the next `wrangler deploy` (`wrangler.toml` has `[vars]` and no `keep_vars`). (Alternative, if the repo's convention of GitHub secrets synced at deploy is preferred: add the GitHub secret, the name to the `secrets:` list AND a `SQUIGGLE_CONTACT: ${{ secrets.SQUIGGLE_CONTACT }}` line to the `env:` of `deploy.yml`'s wrangler step in one change; the step is `continue-on-error`, so a missing `env:` line would leave the deploy green and the secret unset, which check 14 would show as PENDING.)
**STAGED** (verifier: squiggle_contact_set @ relay/staged-verification.yml): the secret is set and the relay sends it. Blocked by: the owner's step above. Unblocked when: `GET /squiggle?q=teams` on the deployed relay answers `X-FIELD-Squiggle-Contact: set`. Verify: `staged-verification.yml` (daily 06:00 UTC) runs check 14 of `scripts/verify-staged-items.mjs` (`node scripts/verify-staged-items.mjs`): PASS on `set` when the relay's own read of Squiggle answered 200; FAIL on `invalid` (set but malformed), on a header that is none of the three words (a broken contract), and on `set` with Squiggle answering 403 to the relay (the contact did not buy access); PENDING on `unset`, on `set` with another non-200 status, and on a relay that does not report. Check 14 proves only that the relay sends the address (the `/squiggle` route's own report; the other four request sites build the same headers, asserted by the checks), not that Squiggle accepts it. ## Item 7 — whether the `cf` cache options take effect on Squiggle (unmeasured)

Every relay Squiggle read sends `cf: { cacheTtl, cacheEverything, cacheKey }` (Rule 78's pattern), and the finals read (`src/afl-squiggle.js`) copies it. The review (finding F1) found that `api.squiggle.com.au` is another Cloudflare customer's zone (A records 104.21.4.226 and 172.67.132.143, NS pam/chip.ns.cloudflare.com, read 2026-11-24 through `dns.google`) and that Cloudflare's docs say such a zone "fully controls how its own content is cached within Cloudflare; you cannot override it", and that `cacheKey` is Enterprise-only. Squiggle states "the regular API has a cache in front of it" (its own 2026-03-29 post). So the hourly relay-side cache the earlier commit message and comments described is **unmeasured and probably not in effect**; the claims are removed (comments reworded in `src/afl-squiggle.js`; the finals commit message corrected). Volume is user-driven: a finals day is two Squiggle reads per `/v2/games?sport=afl` request, and the handler's own cache is `max-age=15`. Also unmeasured, and fail-closed (a missing row is null and warned): when a final's Aggregate row first exists in Squiggle once its teams are known (Squiggle pre-creates finals games with null teams and no tips, read 2026-11-25), and what an hour of caching would do to a row that appears after the first read; and whether ESPN's and Squiggle's kickoff instants agree for a RESCHEDULED game (21 of 21 played games agree exactly).
**Ruling needed (owner):** UNMEASURED, and not staged: nothing in the relay can read `cf-cache-status` (no deployed route returns it), so no verifier can say PASS, and a staged claim without an executor is an orphan (`scripts/staged-verifier-check.mjs`). Measuring it is a new dispatch-only diagnostic (a Worker-side read of `https://api.squiggle.com.au/?q=tips;year=2026;team=1;source=8` made twice with `cf.cacheEverything`, the second `cf-cache-status` logged and read with `wrangler tail`): `HIT` means the options take effect and stay; anything else means they do nothing on this host, and the options should be removed and the "cache and re-use data" requirement met by caching in the relay's own KV as Kali's reads do (`relayFetchKV`). Not built here because it adds a route (Rule 39) and AFL has no fixtures until 2027.

## Item 8 — the `/squiggle` route is an open forwarder, and now it signs its traffic with the owner's address (ruling needed)

`GET /squiggle?q=...` (`src/index.js`) forwards any query that contains `q=` to `api.squiggle.com.au`: no allow-list, CORS `*`, no cap, and (`wrangler.toml`: `caches.default` does not work on this `*.workers.dev` Worker) every distinct query is an upstream request. **Measured by the review of Item 4** with the real worker over a stubbed upstream: 300 anonymous cross-origin GETs with distinct `q=` values made 300 upstream requests, and `q=zzz-not-a-query-type` is forwarded too. Until now that traffic carried a User-Agent with no address; now every one of those requests carries the owner's contact address (once the Worker secret is set), so a third party that hammers the route produces complaints, or an edge block, addressed to the owner: which is what a contact address is for, and a consequence worth deciding on. Squiggle's requirements also say not to "Build a website that makes visitors fetch directly from the Squiggle API themselves": the relay fetches, so the client is within the rule, but an open forwarder is not what that rule describes. The client (`jubilant-bassoon/src/legacy/field.js`, read 2026-11-26) sends only `q=games;year=2026;round=N`, `q=standings;year=2026`, `q=tips;year=2026;round=N` and `q=power;year=2026`.
**Ruling needed (owner):** restrict the route to the query types the client and the relay's own tooling use (`games`, `standings`, `tips`, `power`, `teams`; each with `year` or `game`, which Squiggle now requires for `games` and `tips`) and answer 400 for the rest, and/or cap it per caller. **Not built:** changing what an existing route accepts needs authorization (this repo's rules: do not change routes clients depend on), and it is a decision about the relay's exposure, not a bug. **Found on the way, in the client (jubilant-bassoon), not touched:** the year is the constant `2026` in all four calls, which is the same defect class as the journalism year (Part D of the finals CC-CMD) and will serve 2026's AFL fixtures, ladder, tips and power rankings from the first 2027 round.
