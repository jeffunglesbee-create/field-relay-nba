## Task 2: the live census leaves the per-push path (option D, ruled 2026-11-26)

The cost of the step grew with history, not with change: every push re-read every finished capture. A larger constant binds again, by design, in months. Measured before choosing (2026-11-26, the 100 most recent Repo guards runs, all `push`, 2026-11-22T18:49Z to 2026-11-26T02:52Z, saved list): **30 runs a day on average** (23, 33 and 22 on the three full days), 62 success and 38 failure, so about 76 thousand relay requests a day from CI for this one check, and every one of the 24 runs before `db92f6f` failed.

| option | what it is | cost | what it changes about the claim |
|---|---|---|---|
| A. leave it | raise `READ_CEILING` when the COVERAGE line nears it | one line, every few months | nothing; unrelated pushes stay coupled to external data |
| B. wall-clock budget | read until a time budget, print `N of M` | small | census becomes a sample (Rule 91 allows it if printed); the all-history claim is lost |
| C. measure each event once | a baseline of per-path counts, or a memo keyed on `(key, size, uploaded)` (the list route already serves `uploaded` per key), so each run reads only new or changed keys | moderate | keeps "every capture agrees"; cost grows with new events only |
| **D. run it on a schedule, as its own monitor** | the live census leaves `guards.yml` for `bsd-frame-census.yml` (every six hours, on dispatch, and on a push to the census script or the workflow); `guards.yml` keeps the self-test and the mutations | small, no state | keeps "every capture agrees"; stops gating unrelated pushes on external data; about 85% fewer reads |

**Ruling and why it departs from my 2026-11-23 recommendation (C).** The owner delegated the choice. I recommended C on 2026-11-23, before measuring how often the step ran and before seeing the shape of the failure: a monitor of external data was gating every unrelated push, which is why 13 hours of pushes were red with every declared frame agreeing. D fixes that and the cost at once, with no baseline, cache or regeneration rule that could itself go stale in a guard whose purpose is trust. It does not stop the reads per run growing toward `READ_CEILING`; that is Task 3, and D and C compose.

**Built (2026-11-26).** `.github/workflows/bsd-frame-census.yml`: cron `23 1,7,13,19 * * *`, `workflow_dispatch`, and a push trigger on `scripts/check-bsd-frame-contract.mjs` and the workflow file; `contents: read`; the job's limit is 15 minutes and the census step's is 10 (so a stalled relay is a failed step, which the dead-cron watch counts, not a cancelled job, which it does not); it runs the self-test first, then the census with its exit code kept in a variable (not through `tee`, which would have needed an unchecked `pipefail`), and writes the whole census to the step summary. `.github/workflows/guards.yml`: the step is renamed "the BSD frame check's self-test and mutations pass (the census itself runs in bsd-frame-census.yml)" and no longer runs the live command; its comment says why.

**Review before the push (three independent read-only skeptics) and what was done with it.**
- *Protection lost:* nothing about a commit that is not still checked offline: the self-test drives `live()` over a bucket in memory and reads the declaration in `src/index.js` for real; three mutations of the declaration (restoring the 2026-10-10 frame, changing a frame, renaming a key) each turned `--self-test` red on a copy. A declaration edit is pinned offline by the self-test on any push that is not src-only, and read against the captures at the next tick: `src/index.js` was deliberately not added to the push trigger, because 21 commits touched it between 2026-11-22T18:00Z and 2026-11-26 and a run on each would give back most of the saving (this clone is shallow and begins 2026-11-19, so earlier counts are not available here). Comments that said "on every push" were corrected to "every push outside `src/**`, `wrangler.toml` and `workers/**`".
- *Workflow correctness:* the first draft used `set -o pipefail` with `tee`; one reviewer showed that without that line the step would be green on exit 3 and that no gate would notice. It now keeps the exit code in a variable, and the step and the summary were simulated under the Actions shell (`bash -e`) with a stub census exiting 0, 1 and 3: exit codes 0, 1 and 3, and the summary still written; with no `census.txt` the summary says the census did not run. The summary first kept only the first line of each row and now prints the whole census. The mutator was removed from the push trigger (the workflow never runs it). Every repo gate that parses workflows accepts the file (`workflow-yaml-check`: 233 files, 0 failing; timeouts, push-lands, secret writes).
- *Who reads a red:* a push no longer shows it. `scripts/watch-silently-dead-crons.mjs` (daily) lists a scheduled workflow whose last three scheduled runs all failed as new decay and goes red itself, and that watch is on the owner's daily read; the lag is three ticks (about 18 hours) plus the watch's day. The workflow is deliberately not in `docs/declared-detectors.json`: declaring it a detector would silence exactly that alarm. Whether GitHub also emails on a failed scheduled run was not established here.
- *Not built, recorded:* adding the offline self-test to `deploy.yml`, which would pin the declaration on a src-only push too (an improvement beyond the status quo, since a src-only push never ran the old census either). It is in `docs/CC-CMD-2026-10-19-guards-only-src-readers.md`, the document that owns that question.

## Task 3: stop the census's cost growing with history (filed, not yet unblocked)

D leaves the reads per run growing with the bucket: 2531 planned reads on 2026-11-23, a ceiling of 10000, about 22 to 60 reads a day of growth, so about 4 to 11 months to the ceiling. Option C (above) removes that growth; B gives up the all-history claim. **Recommendation: C, as a memo keyed on `(key, size, uploaded)`**, because the list route serves `uploaded` per key (`/bsd/r2/list` returns `{ key, size, uploaded }`), so a rewritten capture is detected rather than assumed away, which was the one cost the first pricing of C carried.

**Unblock criteria (Rule 74).** Unblocked when the census's COVERAGE line reads `N of M planned reads` with `M >= 7000` (70% of the ceiling). Verify: open the latest `bsd-frame-census.yml` run's step summary ("BSD frame census") and read the `COVERAGE:` line. Until then nothing in this task is built and the census going INSUFFICIENT at the ceiling is its own loud failure, now in its own workflow and not on every push. **Done condition:** two census runs a week apart whose planned reads differ by no more than the reads for the keys captured in between.
