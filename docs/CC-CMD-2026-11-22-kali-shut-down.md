## The defect, stated from the code and the probe together

`relayFetchKV` treats any `upstream.ok` as a good answer: `const bodyText = await upstream.text(); await kv.put(cacheKey, bodyText, { expirationTtl: ttl })` (`cache-helpers.js:164-165` at `345715d`; after the fix the parse check is at `:185` and the store at `:190`), and every later hit is served as `Content-Type: application/json` (`:147-150` at `345715d`). Kali's holding page is a 2xx HTML body. So the first AFL call after the season returns would store 5818 bytes of HTML under the Kali URL for `ttl` seconds (3600 at `wp-resolver.js:441`) and replay it as JSON. Both callers then fail to parse it and fall back, so nothing breaks loudly: the cost is a wasted upstream call per cache window, a KV write of a page that is not data, and the `/kali/*` route handing a client HTML labelled JSON. The relay also sends `Authorization: Bearer <KALI_AFL_TOKEN>` (`index.js:4411`, `wp-resolver.js:440`, `index.js:17338`) to that host on every miss; the README says issued keys no longer work.

Nothing calls it today: the AFL offseason has no AFL games (`buildAFLJournalismContext` returns `{}` for an empty slate, `:4382`) and no AFL pick to resolve. Not read: whether `KALI_CACHE` already holds an HTML entry from an earlier call (the Cloudflare MCP lists KV namespaces but this session has no key read).

Impact analysis (Rule 13), from the table above: `index.js:4410` reads `kaliResp.value.ok` and gets `false`, which leaves `kali` as `null`, the same outcome as today's caught parse failure; `wp-resolver.js:438` gets `r.ok === false` and falls to Squiggle, the same outcome as today.
